# Decision log

Each entry: decision, reason, and what would change it. Entries 1 to 5 record how the project changed. Earlier logs: [archive/metal/DECISIONS.md](archive/metal/DECISIONS.md) and [archive/typescript-stack/DECISIONS.md](archive/typescript-stack/DECISIONS.md).

| # | Decision | Reason | Revisit if |
|---|---|---|---|
| 1 | Subject changed from metal artists to music theory and instruments | Research showed the metal corpus was patchy (six headline bands had no page in the `music-wiki` snapshot, no free metal dataset, no permission found for Encyclopaedia Metallum). The new corpus was measured before design. | Never. |
| 2 | Data was verified before design | The metal subject failed on data. Research agents checked licences, fetchability and tools first. | Never. |
| 3 | Audio input (recording, analysis, YouTube links) is out of scope | Audio analysis is a separate signal-processing problem, accuracy on real songs is weak, and YouTube downloads breach its terms. | A later project. |
| 4 | Stack changed from SvelteKit and TypeScript to React and Python (FastAPI) | The author knows React and not Svelte. A plain React app needs a separate backend anyway, so the one-language benefit of SvelteKit was gone. Python gives the most complete LangChain, course-aligned examples, upsert and richer filters in the vector store, and RAGAs in the same project. Two spikes (TypeScript and Python) showed both stacks work with workarounds. | The Python spike's untested areas fail (real model behaviour, OpenRouter cost through `langchain-openai`). |
| 5 | The Python stack costs the verified `tonal` tool layer | `tonal` is JavaScript only. The music tools are the weakest part in Python, see decision 24. | A Python library covers more of the tools. |
| 6 | Scope: music theory and instruments together | A question like "what does a B-flat clarinet sound when it reads a written C" needs both the corpus and a tool. | Never. |
| 7 | Audience: a learner, beginner to intermediate | Tightens the system prompt and the golden set. | Never. |
| 8 | Corpus: about 150 Wikipedia articles plus Open Music Theory v1 | Both CC BY-SA 4.0, structured headings, enough size (about 2,000 to 5,000 chunks), and the two sources use different Conventions. | OMT 2e becomes fetchable, or a text gap appears. |
| 9 | Not used: Wikibooks, LibreTexts books, Open Opus, Met Museum | Wikibooks is thin, LibreTexts licences are mixed (NC, GFDL) with a 5 s crawl delay, Open Opus has no SLA, the Met API has no prose. | A gap in the golden set that these would fill. |
| 10 | Wikipedia pages fetched from the REST HTML endpoint | It keeps headings and tables, `explaintext` flattens or drops them, and the research verified headings in the response. | Table extraction fails for the transposition tables. |
| 11 | Ingestion at about 1 request per second with a User-Agent, one-off script with caching | Wikipedia rate-limited a burst in the research. | Never. |
| 12 | 5,000-character floor for Wikipedia pages | 28 of 190 Hornbostel-Sachs links were stubs under 2,000 characters. | The floor drops needed pages. |
| 13 | Redirects resolved, old names stored as Aliases and prepended to chunk text | Makes "English horn" find "Cor anglais" in vector and keyword search. | Never. |
| 14 | Store `revision_id` and `license` per document, show attribution links | CC BY-SA requires attribution, and pages change daily. | Never. |
| 15 | pgvector in the app's Postgres, behind a `Retriever` interface | One database, SQL filters, hybrid in one query. SRP is satisfied by the interface, not by splitting databases. | Scale, or a reviewer expectation of Chroma. |
| 16 | `langchain-postgres` `PGVectorStore` (v2) for core retrieval, with real metadata columns | Matches the course pattern, gives upsert by id, safe deletes and rich filters (`$or`, `$not`, `$like`). The JS store had no upsert and fewer filters. Pinned to an exact version because it is 0.0.x. | A bug blocks use. Fall back to our own SQL for retrieval. |
| 17 | `topics` stored as a pipe-delimited text column and filtered with `$like` | The library cannot filter array columns. The workaround gives both any-of and all-of. | The library adds array filters. |
| 18 | Deterministic chunk ids (uuid5), re-ingest by upsert then delete stale chunks | The batch insert is not transactional, so idempotency comes from the ids. | Never. |
| 19 | Section-aware chunking from real headings (HTML sections, OMT `##` and `###`), about 800 characters, 100 overlap | Keeps topics separate and gives Citations a section. | Retrieval eval shows poor recall. |
| 20 | HNSW index with a custom `QueryOptions` setting `hnsw.iterative_scan = relaxed_order` | A selective filter returned 0 rows with the index forced until the setting was applied. | Postgres keeps using sequential scans at our size, then the index is optional. |
| 21 | `create_agent` with retrieval as a tool, no router | Matches the course, less code, decomposition comes free through the tool loop. | Agent loops cost too much. |
| 22 | `AsyncPostgresSaver` on a connection pool for memory, `aget_state` for export | Verified with a fake model: memory across turns, isolated threads, full message list for export. | Real-model behaviour differs, or partial checkpoints after disconnects cause trouble. |
| 23 | Query translation: multi-query inside the retrieval tool, decomposition via the tool loop, structured args. No HyDE or step-back. | Fits the use cases and the budget. | Eval shows recall problems HyDE might fix. |
| 24 | Music libraries: `pychord` (chords), `music21` (scales, intervals, keys), hand-written `note_frequency` and instrument offset table | `pychord` matches `tonal` for chords including ambiguous detection. `music21` is the only credible library for scales and intervals, but is 230 MB and spells flats with `-`. `mingus` is GPLv3 and unmaintained, `musthe` is from 2018. | `music21` proves too heavy, then hand-write scales and intervals (about 100 lines). |
| 25 | Six tools: knowledge base search plus `chord_info`, `scale_info`, `interval_between`, `transpose_for_instrument`, `note_frequency` | At least 3 required, all deterministic and testable. `harmonic_series` is a stretch. | Time pressure: drop `scale_info`. |
| 26 | Libraries raise on invalid input, tools catch and return structured errors | `H4` and `Xyz` raise in both libraries. Structured errors are better for the model than silent empties. | Never. |
| 27 | Transposition table of about 14 instruments, each with a Citation | No library has curated, citable instrument data. | Never. |
| 28 | Tools use scientific pitch notation (C4 = middle C) and state it | Sources disagree on conventions. Stating the tool's Convention stops silent contradictions. | Never. |
| 29 | Convention conflicts are shown side by side with a Citation each, no winner | Matches how sources actually differ, easier to verify, clear faithfulness test. | Never. |
| 30 | Ambiguous analyses return all Candidates | `pychord` gives `[Dm7, F6/D]` for D, F, A, C. | Never. |
| 31 | Answer only from retrieved context and tool results | Keeps RAGAs faithfulness meaningful. | Eval shows too many "I don't know" answers for covered topics. |
| 32 | Hybrid search by our own SQL (RRF), library `HybridSearchConfig` only as a comparison mode | 0.0.19 reuses the first query's keywords unless a fresh config is passed per call. Our SQL is predictable and easy to explain. | The library bug is fixed and the comparison favours it. |
| 33 | Hand-rolled SSE with typed events from `stream_mode=["messages","updates","custom"]` | The event stream is the shared contract for UI, logging and the RAG-process view. Verified with a fake model. | Never. |
| 34 | `fetch` plus a stream reader on the client, Vite dev proxy for `/api` | `EventSource` cannot POST a body, and the proxy removes the need for CORS in development. | A fetch-event-source library saves code. |
| 35 | Chat plus inspector panel UI with Tailwind 4 and DaisyUI 5 | Shows context, sources and tool results, gives the RAG-process view cheaply. DaisyUI works in React. | Never. |
| 36 | OpenRouter for chat and embeddings: `openai/text-embedding-3-small` (1536 dimensions), `openai/gpt-4o-mini` first for answers and rewriting | The JS research tested them end to end. Cheaper models are compared with the tool-calling eval. | A cheaper model passes the eval, a guardrail blocks a model, or `langchain-openai` mishandles cost. |
| 37 | Budget in OpenRouter credits (soft 1, hard 4), treated as USD | `usage.cost` is returned in credits, no price table needed. | The account page shows another relation. |
| 38 | Persistence: Postgres only. Our own tables are SQLAlchemy 2 ORM models (`app/db/models.py`) migrated with Alembic (`app/db/migrations/`), the library's table helper makes the chunk table, and the hybrid query stays hand-written SQL | The author prefers an ORM and a standard migration tool (changed in story 2, was plain SQL files and no ORM). SQLAlchemy is already installed by `langchain-postgres`. SQL stays where it is the point (hybrid query, usage sums). Libraries' tables are excluded from autogenerate. | Alembic adds more friction than the few tables are worth. |
| 39 | Optional tasks: injection protection, cost display, logging (medium), RAGAs, hybrid (hard), citations, history and export (easy), RAG-process view (stretch) | Exceeds the minimum of 2 medium and 1 hard. | Time pressure: drop the stretch, then logging. |
| 40 | Evaluation in three layers, RAGAs in the same Python project | Two layers are free and run on every change. RAGAs is native Python, so no separate container is needed. | RAGAs dependencies conflict with the backend. Then a separate virtualenv or container. |
| 41 | No auth, single local user, English only | Out of scope for the brief and the budget. | Never for this sprint. |
| 42 | `CONTEXT.md` holds domain terms, `GLOSSARY.md` holds technical terms | One glossary for each kind of language. | Never. |
| 43 | Work in stories, not days | The author wants feature-by-feature implementation. | Never. |
| 44 | Docker Compose runs the database, the backend and the client dev server | One `docker compose up` starts the whole stack. Ports and Postgres settings come from the one root `.env`, and the client also runs on the host with `npm run dev`. | The container file watching or HMR is too slow on this machine. |
| 45 | Server data goes through React Query with `queryOptions` and key factories in `src/queries/`, called inline with `useQuery`, not through one hook per query | `queryOptions` keeps key, function and settings together and is reusable for prefetch and invalidation without wrapper hooks. Defaults live in one `QueryClient` (staleTime 30 s, gcTime 5 min, retry 1, no refetch on focus), and a query overrides them where needed. | A feature needs shared logic around a query, then a hook is fine. |
| 46 | Streamed cost comes from a small `ChatOpenAI` subclass that keeps OpenRouter's raw `usage` (with `cost`) on the streamed chunk | Live check: `langchain-openai` drops `usage.cost` on streamed responses, the generation lookup returned 404 and LangChain's chunk id is not OpenRouter's. The raw usage chunk does carry `cost`. The subclass is about 8 lines and puts the cost on the message the cost guard already reads. | The library keeps `cost` on streamed chunks, or the private method it overrides changes (pin `langchain-openai` and test that cost is present). |
| 47 | The transposition table is built from "List of transposing instruments" (sounding pitch of a written C4), and the ingest flattener expands `rowspan` and `colspan` | "Transposing instrument" has no data table, only prose. The list page has one 116-row table, and a plain row-by-row flatten drops the family column. Offsets are derived (sounding minus written), not read. See [research/ingestion-sources-facts.md](research/ingestion-sources-facts.md). | Wikipedia restructures the list page, or the hand-built table is judged enough without it. |
| 48 | Cleaned documents are stored with their sections (`documents.sections`, JSONB), and below-floor Wikipedia articles are dropped from the Corpus unless they are required pages (kept and flagged) | Story 3 chunks from the stored sections, so it does not re-run the HTML cleaning, and the OMT parse needs no cache of its own. The floor report lists every dropped title so the author decides, instead of the script guessing which short articles matter. Migration 0002. | The table gets too large to hold text, or the author wants short theory articles (Minor scale, Dominant) kept regardless of size. |
| 49 | The nine short core pages are kept by name (`KEEP_BELOW_FLOOR`) and the floor stays 5,000; Soprano clarinet is dropped and its Aliases sit on Clarinet; textbook topics come from a hand-written slug table, with two new topics, `counterpoint-and-voice-leading` and `post-tonal` | The ten pages below the floor were 1,434 to 4,445 characters and nothing else sits near it, but lowering the floor would loosen it for every later entry. The Soprano clarinet article is a stub, so Clarinet carries its names. The book's chapters on species counterpoint, figured bass and set theory fit no existing topic, and a catch-all would make the filter useless. Issue 15. | A kept page turns out too thin to answer from, or the textbook gets a second edition with a new table of contents. |
| 50 | Embeddings are requested straight from `POST /embeddings` with `httpx` (batches of 100 to 256), and `usage.cost` is read from the response body | Issue 16: the endpoint returns `usage.cost` on every call, but `OpenAIEmbeddings.embed_documents` returns only vectors, so the cost would be lost. The full Corpus is about 6,400 chunks and costs about 0.02 credits, so the budget is not at risk. See [research/embeddings-sample.md](research/embeddings-sample.md). | The real splitter changes the chunk count a lot, or `langchain-openai` starts returning usage for embeddings. |
| 51 | Chunk ids are uuid5 over the document's URL, section index and chunk index; the chunk `aliases` column is pipe-delimited like `topics`; the splitter is LangChain's `RecursiveCharacterTextSplitter` (800 characters, 100 overlap, pinned `langchain-text-splitters`) | The URL is the document's identity (unique in `documents`), so ids survive a rebuilt database, where the row id would not. A TEXT column filtered with `$like` needs the same pipe format as `topics`. A known splitter beats 40 lines of our own, at the price of one small dependency; it breaks at paragraph, line and space but not at sentence ends. Stored Corpus gives 7,329 chunks (the 6,431 in decision 50 was a rough estimate), 971,863 tokens and 0.0194 credits to embed. Issue 17. | Section order changes between ingests often (the section index would shift every id after it), or recall shows 800 characters is too small. |
| 52 | Every dense query runs with `hnsw.iterative_scan = relaxed_order` (`HnswIterative` in `app/rag/vector_store.py`, passed as `index_query_options`), and the HNSW index is created even though the planner does not use it yet at 7,329 chunks | With an index scan forced, filters returned 7, 0 and 0 rows without the option and 10 with it. The option reached the query's connection in every one of 16 concurrent searches through a pool of one. The index costs little and the filters stay correct if the Corpus grows or the planner changes. See [research/hnsw-iterative-scan.md](research/hnsw-iterative-scan.md). | The library stops applying `SET LOCAL` on the query's connection, the app moves behind PgBouncer, or Story 15's hybrid query replaces the library's dense query. |
| 53 | The baseline `Retriever` calls `PGVectorStore.similarity_search_with_score` and returns our own `RetrievedChunk` (Citation fields, `score` = 1 minus cosine distance), instead of `as_retriever` returning LangChain documents; filters are a small frozen `Filters` dataclass (`source_type`, `topics` with any-of or all-of, `title`) | `as_retriever` drops the score, and the metrics script, the inspector and Citations need it. A dataclass validates `source_type` and the topic mode before any SQL, and lets Story 5's tool and Story 15's hybrid retriever share one call. The method is synchronous for now (the store wraps its async core). | Story 5 needs an async tool, or hybrid search needs filters that do not fit the dataclass. |
| 54 | An ambiguous or underspecified request gets one clarifying question with options taken from the Corpus, before any answer (DOMAIN.md, bot behaviour rule 7) | The author's requirement. A learner who says "guitar" may mean an acoustic, classical, electric or bass guitar, and the Corpus has a page for each, so answering all of them or guessing one wastes the answer. The golden set marks these questions with `expected_behaviour: "clarify"` and the options it expects, so the behaviour is tested. | The bot over-asks (clear questions get a question back), then tighten the rule and add no-clarify cases to the golden set. |
| 55 | The saved `vector-baseline` run (precision@5 0.814, recall@5 0.821 on 14 questions) is the reference for Story 5 and later. Topic filters narrow a request to what the user asked for, they are not the fix for missed pages; multi-page questions are handled by query rewriting and decomposition (Story 5, 13) and hybrid search (Story 15) | Recall@5 is 1.00 on the 7 single-page questions and 0.64 on the 7 multi-page ones, because one page fills the top 5 (q09: five Viola chunks, no Violin). Even filters built from the expected pages' own topics add only 0.029 precision and no recall. See [research/retrieval-baseline.md](research/retrieval-baseline.md). | Rewriting and hybrid search do not raise multi-page recall, then cap chunks per page or retrieve per entity. |
| 56 | The system prompt carries three worked examples of the clarifying question (drum, clarinet range, "play it an octave lower"), with subjects that are not in the golden set | Issue 32: with rules alone `gpt-4o-mini` answered "Tell me about the guitar." and the saxophone range question. Examples with other subjects fixed both, and the golden-set questions stay a fair test. | The tool-calling eval (Story 9) shows the clarify cases failing again, or a stronger model follows the rules without examples. |
| 57 | A client disconnect leaves the partial turn in the checkpoint, and we keep it | Issue 35 (real model): cutting the stream mid-answer left the user message, the tool call and the tool result with no final answer, and the next message on the thread worked and saw them. A cut before the first token left only the user message. Dropping the partial turn would need extra checkpoint surgery for little gain. | A model rejects a history that ends in a tool result or two user messages in a row, or Story 6's UI shows the orphaned question as confusing. |
| 58 | `search_knowledge_base` emits `citations` and `queries` only when it found chunks; an empty search emits neither | Issue 41: the tool result already tells the model nothing was found, and an inspector row or chip list with no items has nothing to show. The UI treats a missing event as "no sources this turn". | The inspector should show that a search ran and found nothing (then emit `queries` always). |
| 59 | The tool-calling eval (`scripts.eval_tools`, `data/golden-tools.json`, 20 cases) answers searches with a stub retriever by default, so it needs no Postgres, and compares tool names as a multiset and only the arguments a case lists | Issue 53: tool selection depends on the question and the tool descriptions, not on the retrieved text, and the stub says it is enough so the agent does not search again. A first run on `gpt-4o-mini` took 72k tokens (about 0.015 credits). Free-text arguments (`query`) are not scored; spellings the tool accepts are listed with `any_of`. | Selection depends on what search returns (clarify cases need real page titles), then run with `--real-retriever` or add a case type for it. |
| 60 | Keep `openai/gpt-4o-mini` as the chat model. `google/gemini-2.5-flash-lite` is the alternative to watch | Issue 55, same 20 tool-calling cases: `gpt-4o-mini` 1.00 selection and 1.00 parameters for $0.0120, `gemini-2.5-flash-lite` 0.95 and 1.00 for $0.0061 (it over-searched one comparison), `gemini-3.1-flash-lite` 0.85 and 1.00 for $0.0219 (dearer and worse). The saving is about 0.006 credits per 20 questions, small next to the 1-credit target, and `gemini-2.5-flash-lite` was rate-limited upstream (HTTP 429) in two of four runs. See [research/tool-calling-baseline.md](research/tool-calling-baseline.md). | Cost starts to matter (many more questions per run, the RAGAs judge calls), `gemini-2.5-flash-lite` runs without 429s and matches `gpt-4o-mini` on the RAGAs answer metrics, or OpenRouter retires `gpt-4o-mini`. Switching is `OPENROUTER_CHAT_MODEL`, then re-run `scripts.eval_tools --label`. |
| 61 | Multi-query rewrite runs inside `search_knowledge_base` with `OPENROUTER_REWRITE_MODEL` (default `openai/gpt-4o-mini`): the original query plus up to 2 rewrites are each retrieved at k, interleaved best-first, de-duplicated by chunk id and cut to k overall. A failed or empty rewrite searches the original only. The agent's tool arguments are unchanged, and `build_agent` rewrites only when given a `rewrite_model` (the tool eval does not) | Issue 58: the tool schema and `scripts.eval_tools` stay untouched. Interleaving lets each wording contribute a page, where sorting by score would let one page fill the top k (decision 55). The model call is a hook for `usage_log` in Story 11. | Metrics with and without rewriting (issue 59) show no gain, or k overall hides pages a comparison needs. |
